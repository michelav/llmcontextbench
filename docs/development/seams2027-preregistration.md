Status: **binding** from 2026-10-15. The v2 baseline is frozen and the selection rules
have been applied to it (see "Parameter selection on v2 calibration"). Nothing below

## Questions and hypotheses

| RQ | Hypothesis | Evidence |
|---|---|---|
| RQ1. When does runtime adaptation of context provisioning pay off? | Adaptation pays off only when (C1) the best configuration changes over time, (C2) the change cannot be predicted from request features, (C3) a feasible fallback exists, (C4) the change lasts longer than detection lag, and (C5) probing is cheap. | Replay opportunity map across scenarios (below), including negative points. |
| RQ2. When the conditions hold, does feedback reduce violations or cost? | **H2a (S-D):** a lean-first cascade reaches the default configuration's pass rate at lower token cost. **H2b (S-A):** the v2 router has fewer deadline misses than the frozen router when lean local MCP degrades, at a token cost below fixed inline. **H2c (S-E):** when inline (the incumbent) degrades, the v2 router has fewer deadline misses than the frozen router and uses fewer tokens, by moving to MCP lean; any pass-rate cost is reported. | Live paired episodes, seeds 301–303. |
| RQ3. How fast does it react, and what does it cost? | v2 reacts within 5 requests of onset and returns within 8 requests of recovery; controller overhead p95 < 5 ms. | Live `lags`, `controllerMsP95`, probe cost. |
| RQ4. Which design choices matter? | Feasible fallbacks (scenario design) matter more than controller details; among controller details, estimate expiry and probe rate dominate recovery. | v1 vs v2 live; replay ablations. |

## Evidence available before collection (exploratory)

All of the following is exploratory. Replay used v1 calibration observations
(`studies/replay-v1calib/`), and the cascade figures reuse held-out v1 executions.

- **Lean-first cascade, counterfactual on the v1 fixed arms** (`llmctxbench study counterfactual`):
  - 0 failures over 288 requests, against 26 for fixed lean and 2 for fixed default;
  - ≥ 8.77k tokens per request, against 13.7k for default and 16.8k for inline;
  - p95 latency 18.2 s.
  
  All lean failures were step-limit errors on `rs_004` and `py_005`.
- **Replay fidelity:** the v1 latency scenario reproduces live deadline misses per episode (inline 32.5 vs 30 live; frozen 35.1 vs 34; adaptive 44.1 vs 46).
- **S-A at L10000, 2 s per tool call, requests 31–60:**
  - deadline misses per episode: frozen 15.8, v1 9.8, v2 candidate 5.2, oracle 2.3;
  - v2 tokens are about 1.30M per episode, against 1.15M for frozen and 1.57M for inline.
- **Negative points:**
  - an 8 s limit leaves no opportunity, because MCP's own tail violates it (C3);
  - the token-quota flip (S-B) adds nothing beyond its delay phase, since a single-client trailing quota slows every configuration;
  - MCP faults with local functions as fallback (S-C) are dominated by fixed functions (C1).

## Live studies

Both use the v2 baseline `baselines/repoqa-long64-v2/frozen.json`. Definitions are
generated by `tools/seams/make_grids.py`.

**S-D cascade** (`examples/studies/study.seams-cascade.json`)
- **Arms:** fixed inline, MCP default, MCP lean, function default, function lean; `cascade-mcp` (lean→default), `cascade-mcp-inline` (lean→inline), `cascade-fn` (function lean→function default).
- **Matrix:** stationary; 3 seeds = 24 episodes (2,304 scheduled requests plus fallbacks).
- **Primary contrast:** `cascade-mcp` vs `mcp-default`, on `tokensLowerBound` per request and on `passed`.
- **Secondary contrasts:** `cascade-mcp` vs `mcp-lean` and vs `inline`; `cascade-fn` vs `function-default`; `mcp-lean` vs `function-lean` (does lean fail because of the surface or the transport).
- **Reporting:** per-target breakdown, because failures concentrate on two targets.

**S-A degradation** (`examples/studies/study.seams-degradation.json`)
- **Pair:** inline + lean local MCP (amended; see the deviation record below).
- **Arms:** fixed inline, fixed MCP lean (`cheap`), frozen router, v1 router, v2 router (`v2-rr10-ttl8`), `schedule` oracle (an upper bound, not deployable).
- **Scenarios:** `stationary`, and `mcp-lean-degraded` (3000 ms per tool call on MCP lean for requests 31–60); latency limit 14000 ms.
- **Matrix:** 6 arms × 2 scenarios × 3 seeds = 36 episodes (3,456 requests).
- **Primary contrast:** v2 vs frozen on `deadlineMiss` in `mcp-lean-degraded`.
- **Secondary contrasts:** v2 vs v1; v2 vs inline (tokens); v2 vs oracle (regret); v1 vs frozen; the stationary scenario as a control for exploration cost.

## Parameter selection on v2 calibration (before any pilot)

Original rule (kept for the record):
1. Replay `examples/studies/replay/degradation.grid.json` (inline + MCP default) on the v2 baseline.
2. **Latency limit and delay:** among `n30` points with limit 10000 or 12000 ms and delay 2000 or 3000 ms, choose the largest frozen − oracle miss gap; ties go to the smaller delay.
3. **v2 settings:** among `v2-rr10-ttl12`, `v2-rr10-ttl8`, `v2-t8-ttl8` and `v2-t10-ttl10`, choose the fewest mean misses at that point, subject to:
   - stationary misses ≤ frozen + 1 per episode;
   - stationary tokens ≤ 1.15 × frozen.

   Ties go to the lower recovery lag.

### Outcome and deviation (2026-10-15)

**Calibration drift.** v2 vs v1 calibration (`tools/seams/compare_baselines.py`; full
table in `baselines/repoqa-long64-v2/drift-v1-v2.json`):
- MCP default mean latency rose 32–43 % (p90 8–10 s → 13–14 s);
- the other configurations rose 0–19 %;
- tokens and pass rates are essentially unchanged.

**The original rule fails closed.** At 10–12 s, fixed MCP default misses 33 of 96
requests even without delay, and the frozen router already routes almost everything to
inline. Opportunity is negative at every eligible point (largest: −3.5 at
L12000/3000 ms). `select_parameters.py` now exits non-zero on a non-positive gap.

**Amendment.** It was decided before any pilot and uses calibration data only.
- **Pair.** The cheap configuration becomes MCP lean.
- **Limit.** It is fixed, not searched: the smallest grid limit (12000/14000/16000 ms) at or above the configuration's largest per-bin calibration p90. This is condition C3: the cheap configuration is feasible when nothing is disturbed.
- **Unchanged.** Steps 2 (delay by opportunity, here among 2000/3000 ms) and 3 (policy and stationary constraints).
- **Function lean pair (inline + function lean).** It was evaluated with the same rule, using request-scope delays of 6000/9000 ms, since function runtimes support only request delay (about 3 tool calls per request).
  - Its limit is L16000 (function lean p90 up to 15.2 s).
  - It **fails closed**: no candidate meets the stationary token constraint. v2 spends about 1.5 × frozen without any disturbance, because function lean's heavy tail keeps triggering switches to inline.
  - It is reported as a replay-only negative case (C5, exploration cost) and is not collected live.

## Addition before any pilot: S-E inline degradation (2026-10-15)

Added after the S-A selection and before any pilot episode ran, on calibration data only.
Exploratory replay of two further ideas came first:
- **Inline degradation:** positive at strong delays, so it is added below.
- **Token cap with latency as the objective:** a static per-size rule (small and medium to inline, large to lean) matched the ledger-feedback `pace` policy: 5.2 misses at 0.70M tokens, against 4.1 misses plus 3.4 unserved at 0.99M, at a 1.0M cap. Token cost is predictable from request size, so C2 fails. It is reported as a replay-only negative case.

**S-E definition** (`examples/studies/study.seams-inline-degradation.json`)
- **Pair:** inline + MCP lean. Inline is the incumbent because lean misses the limit at its calibration p90.
- **Arms:** fixed inline, fixed MCP lean (`cheap`), frozen, v1, v2, `schedule` oracle (inline outside the disturbance, lean during it).
- **Scenarios:** `stationary`, and `inline-degraded` (a request-scope delay on inline for requests 31–60).
- **Matrix:** 6 arms × 2 scenarios × 3 seeds = 36 episodes (3,456 requests).
- **Primary contrast:** v2 vs frozen on `deadlineMiss` in `inline-degraded`.
- **Secondary contrasts:** v2 vs frozen on `tokensLowerBound`; v2 vs fixed MCP lean and vs inline; v2 vs oracle; v1 vs frozen; `passed` for every contrast (quality cost of moving to lean).

**S-E selection rule** (`select_parameters.py --infeasible-config local-mcp-lean --feasible-config inline-code-full`):
1. **Limit:** the largest of {9000, 10000, 11000} ms below MCP lean's smallest per-bin calibration p90, provided inline's largest p90 is within it.
2. **Delay:** among {3000, 6000, 9000} ms at `n30`, the largest frozen − oracle gap.
3. **Policy:** among the same 4 candidates, with the same stationary constraints as S-A.

### Pilot outcomes on v2 (2026-10-15)

All 12 pilot episodes completed (480 requests, 5.3M answer tokens, 74 min), were evaluated
and analyzed; no request was unserved. Gates were checked with `tools/seams/pilot_gates.py`.

| Pilot | Gate | Value | Result |
|---|---|---|---|
| P1 | `cascade-mcp` final failures = 0 | 0 | GO |
| P1 | tokens ≤ 0.8 × `mcp-default` | 300,705 / 203,744 = 1.48 (lower bound) | **NO-GO** |
| P1 | fallbacks only on trigger classes | 8 of 8 fallbacks carry `step-limit` | GO |
| P1 | attempts logged with provenance | yes | GO |
| P2 | v2 reaction lag ≤ 5 | 0 | GO |
| P2 | v2 recovery lag ≤ 8 | 5 | GO |
| P2 | v2 delay-phase misses ≤ 50 % of frozen | 5 / 8 = 62 % | **NO-GO** |
| P3 | v2 reaction lag ≤ 5 | 2 | GO |
| P3 | v2 recovery lag ≤ 8 | 9 | **NO-GO** |
| P3 | v2 delay-phase misses ≤ 75 % of frozen | 11 / 14 = 79 % | **NO-GO** |
| P3 | v2 episode tokens ≤ frozen | 577,642 vs 764,026 | GO |

Notes:
- **Gate-script correction:** the first version of the fallback check required every failure class of a fallback to be a trigger class. One step-limit failure also carries the generic `operation` class. The cascade falls back when any trigger class is present (`decide_fallback`), so the check was corrected to match; the criterion itself is unchanged.
- **P1:** half of the pilot targets were chosen because lean fails on them, so the token gate is harsh on this workload. On the two control targets the cascade used 0.74 × default; on `py_005` and `rs_004` it used 1.8× and 2.2×. Lean failed 6 of 6 on `rs_004` (v1: some passes). Function lean failed on the same targets, so the failures come from the lean surface, not the MCP transport.
- **P2:** v2 had the fewest misses of any arm; the gate was missed by one request.
- **P3:** v2 moved to MCP lean within 2 requests, but lean misses the 10 s limit most of the time at v2 provider latency (C3 fails: no fast fallback). It returned to inline late, so over the whole episode it missed 15 deadlines against frozen's 14.

## Amendment after the v2 pilots: v3 catalogue with a direct surface (2026-10-15)

This is the one fix allowed by the pilot rules, applied to the configuration catalogue.
It was made after the negative pilots and before any confirmatory collection, and the paper
reports it as such.

- **Change:** a task-oriented operation `find_symbol(workspace_id, query, k)` ranks callable symbols by BM25 over name, documentation and code, and returns the top k with complete code. The configuration `local-mcp-direct` offers `find_symbol`, `list_symbols_lean` and `get_symbol_lean`. Commit `734b092`; design notes in `docs/development/ideas/repoqa-interface-redesign.md`.
- **Why:** the v2 pilots and the interaction analysis showed that tool configurations are slow because of about 4 sequential model calls, and that no fast, cheap fallback existed (P3). The direct surface targets that cause.
- **Evidence before adoption:**
  - offline ranking check (no provider calls) using the task description as the query, over all 120 long64 instances, held-out ones included: target in the top 5 for 110 of 120. The only design choice made after this check was restricting the ranking to functions and methods;
  - provider mini-check on the 4 calibration targets only (`experiment.repoqa-direct-check.json`, 96 requests): direct passed 48 of 48, median 4.0 s, p90 6.0 s, 2.19 model calls, 3.2k tokens per request; inline passed 48 of 48, 3.5 s, 5.0 s, 16.3k. Request durations in that run have 1 s resolution; provider-reported model time agrees (3.6 s against 3.4 s median).
- **Consequences:**
  - the v2 baseline no longer verifies (fingerprinted sources changed). A v3 baseline (`examples/studies/baseline.repoqa-long64-v3.json`, experiment `experiment.repoqa-long64-v3.json`; same split, seeds and repeats; six configurations) replaces it. Code freeze tag `seams-v3-freeze`;
  - the v2 selections above are superseded. The same selection rules are applied to v3 calibration, and the v3 scenario set, parameters and pilot definitions are recorded here before any v3 pilot runs;
  - v3 pilots use new seeds (904+) and the gates above. They are the re-pilots allowed by the rules: a scenario that fails its v3 pilot is dropped;
  - S-D does not depend on the direct surface. Whether it is collected despite its P1 token gate is decided, and recorded here, before collection.

## Stopping rules and reporting

- **Collection order:** S-D, then S-A, then S-E. Collection is seed-major, with arm order shuffled within each seed, and episode wall-clock times are recorded.
- **No mid-collection changes:** no parameter or code changes during collection. A defect that invalidates results stops the collection; it is then reported and a new seed set is used.
- **Reporting:**
  - v1 results are reported as collected;
  - replay results are labelled `estimated`;
  - the cascade evidence is labelled exploratory where it reuses v1 held-out data;
  - the same 16 held-out targets are reused from v1, and the paper says so.
- **Uncertainty:** report effect sizes with target-cluster bootstrap intervals; no claims beyond them.
